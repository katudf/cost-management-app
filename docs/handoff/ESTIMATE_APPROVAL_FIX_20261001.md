## 修正1: 申請前に最新の内容を保存する（P1）

対象: `src/estimate-editor/EstimateEditor.jsx` の `handleSubmit`、`persistStatus`、`handleSave`、`src/components/estimate/EstimateSidebar.jsx`。

現在、申請はステータスと承認者だけをUPDATEし、未保存の表紙・明細を保存しません。新規見積ではIDがnullのままUPDATEされます。既存見積でも「保存→編集→申請」の変更は承認者に渡りません。

- 保存の検証・ペイロード作成を共通化し、申請時には最新の表紙・シート・明細を保存すること。
- 新規見積では採番されたIDをその処理内で受け取り、確実に同じ見積を申請すること。Reactのstate更新完了を前提にしないこと。
- 保存・申請失敗時は成功表示や画面遷移を行わず、入力内容を保持して `showToast(..., 'error')` で通知すること。
- 処理中の申請・保存の重複実行を防止すること。
- 可能なら修正3のDBトランザクションに申請遷移を含め、下書き保存だけ成功して申請が失敗した場合も状態を明確に扱うこと。

受け入れ条件: 新規未保存から申請可能。既存見積の未保存変更も承認者側の再取得結果に反映。入力不備や保存失敗では申請状態に遷移しない。連打で重複見積・重複申請が生じない。

## 修正2: UIとDBの編集制限を一致させる（P1）

UI対象: `EstimateEditor.jsx` の `originalStatus`、`isLocked`、`persistStatus`、承認・差し戻しハンドラ。親の `src/AdminApp.jsx` の `onStatusChanged` は一覧更新だけでエディタを再読込しません。

DB確認対象:

- `supabase/migrations/20260713004858_split_estimates_office_all_policy_by_command.sql`
- `supabase/migrations/20260713020737_restrict_estimate_draft_revert_to_creator.sql`
- `supabase/migrations/20260710002254_phase2_estimates_purchase_projects_rls.sql`
- `supabase/migrations/20260910231843_fix_function_search_path_and_anon_exec.sql`
- 稼働DBの `estimates` / `estimate_items` / `estimate_sheets` のRLS・トリガー・保存RPC

UIは `originalStatus` でロック判定しますが、ステータス変更成功時に更新しません。DB側は承認証跡と下書き戻しを保護する一方、記載SQLでは下書き以外の内容変更を一律には拒否していません。admin/officeの明細更新も親見積の状態に依存していません。

- 申請成功時点で、再読込を待たずに入力・保存をロックすること。状態判定の情報源を整理し、承認・差し戻し後も整合させること。
- DBでも、下書き以外の見積の内容変更を拒否すること。表紙だけでなく、明細・シートの直接INSERT/UPDATE/DELETEと保存RPC経由を対象にすること。
- 許可する状態遷移と内容編集を分けること。承認RPC、差し戻しRPC、提出済み、受注、失注、論理削除・復元、作成者/adminによる下書き戻しを壊さないこと。
- 申請後の承認者変更や、承認証跡を残したまま内容だけ変更する経路を塞ぐこと。
- 保存と承認の競合を親見積の行ロック等で防ぐこと。明細更新経路も同じ親の状態・ロックを確認すること。
- 既存マイグレーションを変更して済ませず、追加マイグレーションで対応すること。稼働DBとの差分と適用状況を報告すること。

受け入れ条件: 申請直後からUIロック。許可されたDBロールでもpending/approvedの内容変更は直接操作・RPC双方で拒否。指名承認者以外は承認不可。二重承認や保存との競合で承認内容が変わらない。正式な下書き戻し後のみ編集可能。

## 修正3: 表紙・シート・明細を一体で保存する（P2）

対象: `EstimateEditor.jsx` の `handleSave`、`src/supabaseEstimates.js`、保存RPC。

現在は表紙INSERT/UPDATEとシート・明細保存RPCが別リクエストです。明細保存だけ失敗すると、表紙の合計と明細が不一致になります。新規保存では表紙だけ残り、再保存時の見積番号重複にもつながります。

- 新規・更新とも表紙／シート／明細を単一DBトランザクションで保存すること。
- 途中失敗では全体をロールバックすること。明細全削除・再INSERTの既存RPC内部だけでなく、表紙も対象にすること。
- シート仮ID→実UUID、明細リンク、採番重複チェック、計算結果の整合性を維持すること。
- 見積番号の競合はDBの一意制約でも防止し、ユーザーに理解できる通知を返すこと。
- RPCに認証・ロール・見積状態・所属シートのチェックを設けること。SECURITY DEFINER採用時は明示的な権限制御と固定search_pathを必須とすること。
- 保存成功時のみID・スナップショット・dirty状態・ローカル退避を更新すること。

受け入れ条件: 明細保存失敗を注入しても表紙・合計・明細・シートが一切部分更新されない。新規失敗では孤立した表紙を残さず、再試行で正常保存できる。

## 修正4: 空の支払条件を維持する（P2）

対象: `EstimateEditor.jsx` の読込処理 `payment_terms: est.payment_terms || '従来通り'`。

- 新規時の既定値と、既存見積の保存値を分けること。
- 保存済みの空文字をそのまま復元すること。nullの扱いは既存データの意味を確認して決め、説明すること。
- 保存→再表示→プレビューでも空欄が維持されること。

## 小さな表示不具合（併せて修正）

自動退避表示が「NaN日前」になります。`EstimateEditor.jsx` は `lastDraftSavedAt` にISO文字列を入れ、`estimateDraftV2.js` の `formatDraftAge` は数値時刻として減算しています。型を揃え、不正な時刻を表示しないようにしてください。

日付欄は今回の自動操作でfill後に値が戻りましたが、キーボード操作で確定できました。アプリの不具合とは断定していません。手操作で再現する場合のみ修正対象にし、承認済みデータの日付は変更しないでください。

## 維持する承認処理

`approve_estimate` は `auth.uid()` と担当者を照合し、pendingと指名承認者をチェック、`FOR UPDATE`でロックし、DBの `now()` で証跡を記録しています。この仕組みを維持してください。UIだけの権限チェックへ置き換えないでください。証跡はRPC後にDB値を再取得してください。

作成者表示は選択した `staff_id` に対応し、操作ログイン者とは異なります。今回はadminが冨士菜々聖を指定して作成した意図的な操作です。この仕様を本件で変更しないでください。
